# Content Verification

**BlaxkVERSE** · BLAXK BYTE TECHNOLOGIES · snapshot date **2026-10-15** · raw data: `evidence/content-verification.json`

> The master specification's hard rule is that nothing on this site may be invented: no fake projects, no fake metrics, no fake clients, no fabricated contributions, no asserted legal status. This document is the record of how that rule is enforced rather than merely intended — and, importantly, of the times the enforcement caught **this build's own content** being wrong.

---

## 1. The enforcement mechanism

`tools/verify-content.mjs` is a gate, not a report. It exits non-zero, and it is designed to be run after any content change. It performs four classes of check:

| Class | What it does |
|---|---|
| **Internal consistency** | Unique slugs, valid statuses, ownership, required fields, limitations present |
| **Prohibited claims** | Registration status, certifications, personal email, phone numbers, and numeric claims in prose with no recorded field behind them |
| **Excerpt integrity** | Every excerpt has a commit, a path, a line range, a body of exactly matching length, and an explanation; and the body is scanned for credentials, personal data and internal addresses |
| **Live cross-check** | Every repository, exclusion and account is re-fetched from the GitHub API and compared with the record; excerpt files are re-fetched at their pinned commits and compared with the published text |

## 2. What it caught in this build

Recording this is the point. A verification process that has never found a problem has not been tested.

### 2.1 Fabrication risk: a paraphrased code excerpt — **found and structurally fixed**

An early version of the BlaXk Housing excerpt was **written from memory rather than quoted**. The verifier's live check compared the published lines against the file at the pinned commit, found they did not match, and reported:

```
! excerpt text differs from source: blaxk-housing
    backend/listings/views.py @ d83ed7f7f6 — the published lines are a paraphrase or the file moved
```

This is exactly the failure the specification warns about, in the most damaging possible place: a page whose purpose is to prove that claims are checkable, containing a quote that was not the actual code. The real source contains `request.META.get('HTTP_X_FORWARDED_FOR', '')` and `listing.views = F('views') + 1`; the published version did not.

**The fix was architectural, not a correction.** Excerpt bodies were removed from the hand-authored file entirely. They are now generated by `tools/extract-excerpts.py`, which:

- reads a cached copy of each source file,
- verifies its SHA-256 against `sources/MANIFEST.json` and **refuses to proceed** if the hash does not match,
- verifies the cached commit SHA equals the pin recorded in `bx-data.js` and **refuses** if it does not,
- slices the exact line range and emits it verbatim (only trailing whitespace is stripped, and that is recorded as the single permitted transformation).

The build step refuses in turn: `tools/build-content.py` aborts if an excerpt's metadata pin and its generated body disagree, and the runtime shows nothing at all if a body's commit does not match the metadata's pin. **Three independent points fail closed.** A hand-typed excerpt can no longer reach the site.

### 2.2 Claims that did not match their evidence — **found and fixed**

Four excerpts declared line ranges larger than the bodies they published (30 claimed vs 14 shown, 38 vs 34, 18 vs 15, 30 vs 21). A range is a factual claim about a file, so overstating one — even in the harmless direction — is the same class of error. All four ranges are now generated to match their bodies exactly, and the verifier fails if `lineCount !== endLine - startLine + 1`.

### 2.3 A false positive that was worth the argument — **allow-listed with reasoning**

The secret scanner flagged the Xposer excerpt for an "internal endpoint" because its docstring contains `http://192.168.1.5:PORT` — the canonical RFC 1918 example, used in the source to explain which address a phone would use.

The tempting response was to edit the excerpt so the scan passed. That would have been the wrong call: editing a published excerpt to satisfy a scanner is a worse sin than the harmless string that triggered it, because it breaks the promise that the code shown is the code that exists. Instead the rule was narrowed to exclude the documented example address (`192.168.1.x`) while still blocking other private ranges, real hostnames, credentials and personal addresses — and the reasoning is recorded in the scanner's source so the next reader does not have to rediscover it.

### On the earlier rate-limit warning

An interim run reported `5 passed · 1 warning` because the unauthenticated GitHub API allows only 60 requests per hour per IP and the session had already spent the budget on evidence harvesting. The verifier degraded to a **warning** — not a pass — because a check that did not run must never be reported as a check that succeeded. The document you are reading recorded that as an open item rather than quietly re-running it later.

The limit reset, the full run completed, and the result is the clean pass above. It is worth stating what changed between the two runs: nothing about the site. The interim run had proven internal consistency and excerpt screening; this one additionally proves, against GitHub's own servers, that all 8 featured repositories exist, are public and are **not forks**, that all 9 exclusions exist, that the superseded namespace still returns 404 as the site claims, and — the one that matters most after the refactor — that **all 4 published excerpts match the raw source file at their pinned commit byte-for-byte**.

That last check is the independent confirmation of §2.1. The excerpts are not self-consistent because the same script wrote and checked them; they are consistent with GitHub's copy of the file.

## 5. What is deliberately **not** claimed

This list is the substantive part of the document. Each item is a claim that would strengthen the portfolio and is therefore tempting — and each is omitted because it cannot be evidenced.

| Not claimed | Why |
|---|---|
| Any project is **shipped** | No project has a verified public deployment. Every deployment URL was checked; none exists. All eight are `prototype`. |
| Users, downloads, requests, uptime, stars-as-traction | Never measured. No such number appears anywhere on the site, and the verifier fails on prose containing a metric word with an unrecorded number. |
| Engineering-scale claims ("handles millions of requests") | Unmeasurable from a local prototype, and false if measured. |
| **Company registration** | Not asserted anywhere. The site says explicitly that it is not claimed because it has not been verified as complete, and the verifier errors if the word "registered" appears outside that disclaimer. |
| Client list, testimonials, logos | None exist to publish. |
| Certifications (ISO, PCI-DSS, SOC 2) | None held. A pattern check fails the build if any appear. |
| Founders, shareholders, capital, family, registration paperwork | Excluded by the specification and by basic discretion. |
| Awards, conference talks, employment history | No verifiable record. The timeline is built only from repository dates. |
| Performance numbers of the *projects* | Only this site's own performance is measured, because only this site was instrumented. |
| "Actively maintained" | A single push is never described that way. Dates are shown as dates. |
| Work under the old namespace `black999-ng` | The account and its portfolio URL return 404, so nothing from it is reproduced, claimed or linked. The site states this plainly rather than ignoring it. |

## 6. Fork and exclusion accounting

Nine repositories are publicly visible under the account but are **not** presented as Blaxk's work. They are listed on `/source` with a reason each, because a portfolio that omits things silently is not being straight with its reader.

| Repository | Reason |
|---|---|
| `AsyncRAT-C-Sharp` | Third-party remote-administration tooling. Not appropriate to exhibit. |
| `Forked` | A publicly documented decompression bomb. Retained as a reference only. |
| `rea-bx`, `Recordly`, `Signova-`, `Blaxk3dsvg`, `moltbot`, `Call-of-Duty-Sol-Ultra`, `public-apis` | Upstream forks. Authorship belongs to the original projects. |

`Signova-` deserves a specific note: the master specification lists it as a candidate project. Verification showed it is a **fork of a sign-language converter by another author**, so it is excluded and credited upstream rather than exhibited. The verifier fails if any featured repository reports `fork: true`.

Information about the remaining repositories under the account (the balance are forks, empty scaffolds, and unmaintained experiments) is summarised rather than itemised; the site says as much rather than implying the list is exhaustive.

## 7. Content rules enforced in the writing

Beyond the automated checks, these conventions govern every page:

1. **Status is a four-word vocabulary** — shipped, prototype, in progress, concept — defined publicly on `/work`, and used identically in every sentence on the site.
2. **Every project states its limits.** The verifier fails a project with an empty limitations list. This is not decoration: it is the reason the pages read as credible.
3. **Every case study carries a provenance strip** naming the snapshot date and stating which figures came from where and what is not claimed.
4. **Empty states admit emptiness.** A project with no committed screenshot shows a designed panel explaining that, rather than stock imagery. A project with no reviewed excerpt shows an empty source chamber.
5. **Screenshots are captioned with their source** and link back to the repository they came from.
6. **"What this is not"** appears on every case study: no public deployment, so it must not be described as live, available, in production, or used by anyone.
7. **Corrections take priority over presentation.** If any claim here is wrong, the first response is to fix the record.

## 8. How to re-verify

```bash
cd blaxkverse
node tools/verify-content.mjs               # full check against the live API
node tools/verify-content.mjs --offline     # internal consistency only
GITHUB_TOKEN=ghp_… node tools/verify-content.mjs   # avoids the rate limit
```

Recommended cadence: after any content edit, and on a schedule (weekly) so that renamed repositories, moved dates and licence changes are noticed by the pipeline rather than by a reader.
