01Capabilities · what I get hired for

What I actually build.

Six services. Each one lists the projects where I’ve actually done it, so you can check before you email. Three more sit further down: I’ll take them on if the work fits, but I’m not selling them as packages yet.

Web applications

offered today
Problem

A product or internal tool that has to exist in a browser and survive real users.

Approach

React or plain web standards on the front, a typed API behind it, and a database chosen for the workload rather than for fashion.

  • Working application
  • Repository you own
  • Written setup and deployment notes

Demonstrated in: BlaXk Housing, EduBlaxk, BlaXk Aggregator

Automation & scripting

offered today
Problem

A repetitive process that costs hours a week and breaks whenever a human forgets a step.

Approach

Python or Node scripts, scheduled jobs, and integrations with the tools already in use — WhatsApp bots, file pipelines, data extraction.

  • Automation with error handling
  • A runbook
  • Logs you can read

Demonstrated in: BlaXk Aggregator, The Migrator

AI integration

offered today
Problem

An AI feature that needs to be genuinely useful, keep the key server-side, and degrade honestly when the model is unavailable.

Approach

Retrieval from your own documents, schema-validated model output, rate limits, cost ceilings and a deterministic fallback so the product still works when the model does not.

  • Server-side AI endpoints
  • Prompt and schema definitions
  • Usage and cost controls

Demonstrated in: EduBlaxk, SABI, FORMA

Local-first & offline tooling

offered today
Problem

Software that must work without a connection, or on data that must not leave the machine.

Approach

On-device models, local storage, and installation that verifies itself instead of failing silently later.

  • Installable tool
  • Local model provisioning
  • Privacy boundary documented in the interface

Demonstrated in: SABI, FORMA, Blaxk Xposer

Systems & network tooling

offered today
Problem

Two machines need to talk to each other, or a device needs to do something the manual does not cover.

Approach

Proxy and relay tooling, service discovery on a local network, firmware-adjacent work, and mechatronics where the software has to meet the physical world.

  • Tooling
  • Test suite for the risky parts
  • Operational notes

Demonstrated in: Blaxk Xposer, Gesture Controls

Also worked in, alongside the services above: Technical consulting & review · Cloud & infrastructure management · Security-oriented services.

04The builder

One person, a wide machine shop.

Blaxk is a developer and automation builder, and a mechatronics engineering student — which is why the work keeps crossing from software into hardware-adjacent territory: computer vision, local speech models, network tooling.

The through-line is not a framework. It is a preference: build the version that runs on your own machine, understand the whole stack, and publish the evidence.
