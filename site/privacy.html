Privacy & AI disclosure

What this site does with your data

The short version: a page view is counted in a way that cannot identify you, an enquiry you send is delivered by email through EmailJS, and nothing else leaves your browser. This page documents that precisely rather than reassuringly, and it is updated whenever the code changes — a disclosure that has quietly stopped being true is worse than no disclosure at all.

1 · Data this site collects

One thing, and nothing that identifies you: a page view is counted.

  • Page views are counted, by this site itself. When a page loads, a small script tells our own server that a page was viewed. It sends four things: the path, the referring address, a coarse screen-width bucket, and the browser's language. There is no third-party analytics product, no Google Analytics, no Plausible, no Umami, no Fathom — the counting is first-party code you can read at api/track.js and assets/js/bx-analytics.js. The exact list below is what is stored, which is less than what is sent:
  • No cookies. None are set, which is why there is no cookie banner — a banner for cookies that do not exist would be theatre. The analytics deliberately uses no cookie, no localStorage and no device identifier, so there is nothing on your device to consent to.
  • What is stored: a count for the page; a bucket for the screen size; the country the request arrived from, as a two-letter code; the hostname of the referrer, so this site knows a link came from one; and a daily visitor hash. That is the whole list.
  • Your IP address is not stored. To count unique visitors without tracking anyone, the address is combined with a random value that is destroyed at the end of each day, reduced to a short hash, and only the hash is kept. It counts one visitor for one day: it cannot be reversed, and it cannot be linked to the same person on any other day, because the value that produced it no longer exists by then. The address itself is never written anywhere. The browser's user-agent string goes into that same one-way hash and is likewise never stored — it is used as an input, not kept as a record.
  • What is sent and then thrown away: the browser's language tag arrives with the request and is not written to the store. Neither is the full referring URL, and neither is the query string — a link to /work.html?theme=ai is counted as /work.html. Paths are normalised before they are stored, so a made-up address cannot be written into the dashboard.
  • Nothing that identifies anyone is stored. No names, no email addresses, no cross-site identifiers, no profiles. The dashboard shows totals, not people.
  • Counts expire after 90 days automatically.
  • You can refuse, and it is honoured. If your browser sends Do Not Track or Global Privacy Control, nothing is counted at all. This is checked in the browser and again on the server, so it holds either way.
  • No third-party requests. No CDN, no webfonts, no embedded video, no social widgets, no tracking pixels. The page-view request goes to this site's own domain. Every asset is served from this site — including the one third-party library the site ships, GSAP, which is vendored into assets/js/vendor/. Your browser makes no request to anyone but us, which you can confirm in your network panel.
  • No fingerprinting. Nothing reads your canvas signature, device list or fonts for identification.
  • No persistent storage of your activity. Motion preference is carried in the URL, not written to your device.

2 · The assistant panel

This is the part most sites are vague about, so here it is exactly.

  • No language model is connected in this build. The panel is a deterministic retriever over a fixed set of verified records that ship with the site. It matches your question against keywords and returns the matching record.
  • Nothing you type leaves your browser. There is no request to any API, ours or anyone else's. Open your browser's network tab and confirm it — that is the point of building it this way first.
  • No conversation is stored. The log lives in the page and disappears when you close or reload it.
  • It will not answer beyond its records. If your question is not covered, it says so and offers the contact route instead of improvising.
  • Its answers cite the record used, so you can check the claim against the page it came from.

The designed production behaviour

The intended production version replaces keyword matching with retrieval over approved content plus a Gemini call, with these rules fixed in advance:

  • The API key stays server-side and is never exposed to the browser through a public environment variable.
  • Input length, content type and output schema are validated; responses are structured and schema-checked before rendering.
  • Per-session and per-IP rate limits, token ceilings and spend ceilings, with abuse controls and observability.
  • Repository text, READMEs and issue comments are treated as untrusted input. Prompt injection is assumed, not hoped against, and the assistant has no tools and no write access.
  • No persistent chat history by default. If retention is ever enabled, it will be disclosed here before it is switched on.
  • Popular answers cached; a deterministic static answer always available when the model fails or the budget is exhausted.
  • Every AI answer is labelled and links to the source it used. The assistant never claims to have read a whole repository when only excerpts were provided.

3 · The contact form

This is the only place on the site where you send something, so here is the whole path it takes.

  • It is delivered, not stored. The message goes from your browser to EmailJS, a transactional email service, which relays it to an inbox as an email. If you gave an address, EmailJS also sends you an acknowledgement quoting what you submitted; that is the only second recipient, and it is the address you typed. The message does not pass through a server belonging to this site, and there is no database, CRM or marketing list for it to land in — there is none here. EmailJS processes both messages in order to send them and keeps its own delivery logs under its policy; it is the one third party the form involves, named rather than hidden behind a "service providers" clause.
  • Five fields and one trap. Name, email, project type, the enquiry itself and an optional deadline. There is also a hidden field a person cannot see and a browser will not fill; anything that fills it is a bot, and its submission is answered with a success message that goes nowhere. If you use a password manager that fills hidden fields, and your message appears to send but never gets a reply, that is the likely cause — send again from a different device or email directly.
  • The reply-to is the address you type. The template sets it from your field, so answering in your mail client reaches me. Nothing is added to any list; the address exists as an email in one inbox and nowhere else.
  • What client-side delivery gives up, said plainly. There is no server here to rate-limit one address at five messages an hour the way the previous endpoint did. The controls that exist are: the honeypot above, EmailJS's own account limits on the sending side, and a reCAPTCHA check on the template — a message Google marks as automated is refused before it counts against anything. That is a different trade, not an absence of one.
  • If it is not wired, it says so. Rather than accept a message and drop it, an unwired form refuses at the button and names the file that needs the keys. A form that pretends to send is worse than one that admits it cannot — that rule survived the change of provider, which is why this section was rewritten instead of quietly left as it was.

The credentials that make a send possible are one public key and three ids — a service, a notification template and an auto-reply template — and the public key is deliberately visible — that is how EmailJS is designed. Which means the account's monthly limit and the template's reCAPTCHA are not optional polish: they are the difference between a contact form and an open mailbox. The trade-off against the previous server-side design is recorded in the project's threat model, in the repository.

4 · Motion, accessibility and your preferences

  • Your system's reduced-motion preference is honoured automatically, and can be overridden with the motion control in the navigation or the M key.
  • The chosen motion level is stored in the URL (?motion=off) so a reduced-motion link can be shared — and so nothing is written to your device.
  • Content is identical in every motion mode. The reduced route removes movement, never information.

5 · Code shown on this site

  • Excerpts come from public repositories and are pinned to a commit SHA, path and line range.
  • They are screened for credentials, secrets, personal data and internal endpoints before publication.
  • They are rendered as inert, selectable text. Nothing from a repository is ever executed in your browser.
  • Third-party forks are credited to their authors and excluded from the portfolio rather than exhibited.

6 · Contact for privacy questions

Use the contact page. If you believe something on this site misrepresents a fact, a project or a person, say so — corrections to the record take priority over presentation.
