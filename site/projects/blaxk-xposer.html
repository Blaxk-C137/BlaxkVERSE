The brief

Problem

Testing a site on a real phone means wrestling a tunnel, a firewall or a host-header rejection. Vite, webpack, Angular, Django, Rails and Next.js all refuse requests whose Host or Origin is not localhost — and a phone that loads your frontend cannot reach your backend, because to the phone 'localhost' means the phone.

Who it is for

A developer with a phone in one hand and a dev server already running on the laptop.

Approach

Xposer reverse-proxies the local port to the LAN and rewrites traffic so the application never notices it moved: Host and Origin headers are translated per request, and URLs inside HTML, JavaScript, JSON, redirects, cookies and CSP headers are rewritten in both directions, including inside gzip-compressed and streamed bodies.

Personal contribution

Sole author. The repository contains the proxy session, the rewriting rules, the port and service detection, the GTK interface and an extensive test suite for the HTTP rewriting.

Decisions that mattered

These are the choices that shaped the code — the ones worth explaining, rather than a feature list.

Rewriting rules are pure functions over strings and bytes

The module docstring says it and the file structure proves it: every rule is unit-testable without opening a socket. On a component where a bug means 'my dev server is now reachable from the coffee shop Wi-Fi', that testability is the safety mechanism.

Streaming bodies are held back, not buffered

A URL can be split across two TCP chunks, so a naive per-chunk replace would miss it. Xposer holds back a tail sized to the longest possible URL literal, which is why a websocket or a live-reload stream does not break the rewriting.

HTTPS dev servers are presented to the phone over plain HTTP

Xposer talks TLS to the application and plain HTTP to the phone, which removes the certificate-warning dead end. Keeping HTTPS end to end is one click away for applications that need camera or microphone permissions.

Non-web services are relayed as raw TCP

A database or an SSH port is not pretending to be a website; it is relayed as TCP, and the interface says so.

Limitations, stated plainly

  • LAN-only by design. Xposer exposes nothing to the public internet, which is the point — and also the boundary.
  • Windows support depends on accepting the platform firewall prompt.
  • It is a desktop tray application, so there is no public deployment to visit.

What this is not: there is no public deployment for this project, so it should not be described as live, available, in production, or used by anyone. Claims about scale or reliability would require measurements that do not exist.

The design contract, in the docstring. This docstring names all three failures the module exists to fix — Host/Origin rejection, a frontend calling the phone's own localhost, and CORS refusal — and then justifies why the implementation is pure functions. It is the clearest statement of the problem in the whole repository.

What it taught

The interesting engineering was all in the seams. Rewriting a response body is easy; rewriting one that is gzipped, streamed, chunked across a boundary and carrying a variation header is a different problem, and the test file grew to be larger than the feature.
