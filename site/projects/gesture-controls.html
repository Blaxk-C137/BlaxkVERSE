The brief

Problem

Whether computer vision can be a usable input device rather than a demo is decided by latency and false positives, not by accuracy on a still image.

Who it is for

An experimental user — this is a testbed, not a product.

Approach

MediaPipe hand landmarks from the webcam feed are mapped to control events for a small game loop, with the frame budget treated as the constraint because the tracker and the renderer share one machine.

Personal contribution

Sole author of the tracking-and-control loop.

Decisions that mattered

These are the choices that shaped the code — the ones worth explaining, rather than a feature list.

Landmarks instead of a trained classifier

Fewer moving parts and no dataset to collect before the first run — appropriate for testing whether the interaction is viable at all.

A gesture must be stable across frames before it counts

Single-frame triggers produced constant accidental input, which is the failure that makes gesture control feel broken rather than imprecise.

Limitations, stated plainly

  • Sensitive to lighting and camera quality.
  • Prototype scope: a demo loop, not a general input framework.
  • MIT licensed.
  • It is a camera application, so it runs on the machine with the webcam.

What this is not: there is no public deployment for this project, so it should not be described as live, available, in production, or used by anyone. Claims about scale or reliability would require measurements that do not exist.
