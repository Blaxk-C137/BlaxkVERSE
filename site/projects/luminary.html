The brief

Problem

Recommendations are siloed by medium. You finish a series and the place that knows you liked it has no idea what to suggest in print, so the decision starts from nothing every time.

Who it is for

People deciding what to watch or read next who do not want to make the decision in four separate apps.

Approach

Four media types are unified behind one interface: films and series from TMDB, anime and manga from AniList through GraphQL, and books from Google Books. Data is fetched with TanStack Query, ephemeral interface state lives in Zustand, and an AI recommendation route uses Gemini to turn a loose request into a pick with a poster.

Personal contribution

Sole author.

Decisions that mattered

These are the choices that shaped the code — the ones worth explaining, rather than a feature list.

Server routes in front of every provider

Each API is reached through a parameter-based route rather than directly from the browser. That keeps provider keys out of client code and gives one place to normalise four differently shaped responses.

Degrade to a retry tile, not a blank screen

A missing key produces a visible retry state with an explanation instead of an empty grid, so a configuration problem is diagnosable by the person seeing it.

Local state stays local

Saved titles live in local storage and ephemeral interface state in a store, with the query cache handling everything server-owned. No account is required to use it.

Limitations, stated plainly

  • Requires three separate provider keys to be fully functional, so a self-hosted copy is partly dark until they are supplied.
  • Recommendation quality depends on the provider metadata available for the title you ask about.

What this is not: there is no public deployment for this project, so it should not be described as live, available, in production, or used by anyone. Claims about scale or reliability would require measurements that do not exist.
