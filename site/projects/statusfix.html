The brief

Problem

WhatsApp re-compresses anything you post as a status, and the result is visibly worse than what went in. The cause is a size ceiling: exceed it and the platform degrades your media to fit. The fix is to arrive under the ceiling on your own terms rather than let the platform decide.

Who it is for

Anyone who posts photos or video to WhatsApp status and has noticed the quality drop, which is most of the people who post at all.

Approach

Images are capped at 1600px on the long edge and encoded to a guaranteed sub-5MB JPEG. Video is transcoded to H.264/AAC at 720p with a two-pass encode sized to land under 16MB, because a single-pass bitrate guess overshoots as often as it undershoots. All of it runs server-side through FFmpeg, bundled via ffmpeg-static so there is no system dependency to install.

Personal contribution

Sole author across three repositories: the Express/FastAPI-tier API that does the encoding, the React client that does the uploading, and a combined deployment repository that serves both from one process.

Decisions that mattered

These are the choices that shaped the code — the ones worth explaining, rather than a feature list.

Two-pass encoding rather than a bitrate formula

A target size is a hard constraint, not a preference. Two-pass measures the actual source before committing to a bitrate, which is the only way to hit 16MB reliably across a 10-second clip and a 3-minute one.

Files deleted immediately after the response

Uploads and outputs live in the OS temp directory and are unlinked the moment the response is sent. Media people post to status is personal, and a service that quietly retains it is a liability in a way that has nothing to do with the feature.

FFmpeg bundled, not assumed

Requiring a system FFmpeg install would have made the project unrunnable for exactly the people most likely to try it. Bundling costs package size and removes an entire class of setup failure.

Limitations, stated plainly

  • It runs from the repository rather than from a hosted URL.
  • Video is capped at 3 minutes by design; longer clips are rejected rather than silently truncated.
  • There is no test suite, so the encode guarantees rest on the author's manual verification.

What this is not: there is no public deployment for this project, so it should not be described as live, available, in production, or used by anyone. Claims about scale or reliability would require measurements that do not exist.

What it taught

Encoding parameters should be expressed as the outcome you need rather than the mechanism you use. "Under 16MB" is checkable; "CRF 23" is not.
